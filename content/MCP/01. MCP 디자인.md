# 설계 문서: VNTG Claude Code 표준 관리 구조

작성 2026-08-21. 대상: 결정권자 및 개발플랫폼팀.

## 1. 해결하려는 문제

지금 각자의 `~/.claude/` 는 개인이 알아서 채우는 영역입니다. 이 상태의 문제는 3가지입니다.

1. **표준이 없다.** 코드리뷰 기준, 커밋 규칙, Jira 이슈 형식이 사람마다 다릅니다.
2. **좋은 설정이 전파되지 않는다.** 누가 유용한 스킬을 만들어도 개인 폴더에 갇힙니다.
3. **가드레일이 없다.** 시크릿을 코드에 쓰거나 위험한 명령을 실행하는 것을 막을 장치가 없습니다.

동시에 반대 방향의 요구도 있습니다.

4. **프로젝트마다 개발환경이 다르다.** Spring 프로젝트와 React 프로젝트에 같은 빌드 명령을
   허용할 수 없습니다. 전사 표준으로 다 정할 수 없습니다.

즉 **전사 공통은 중앙에서, 프로젝트 고유는 프로젝트에서** 관리해야 합니다.

## 2. 설계 원칙

| 원칙 | 이유 |
| --- | --- |
| 계층은 3개까지만 | 4개 이상이면 "이건 어디에 넣지"에 답할 수 없습니다 |
| 각 계층의 소유자가 명확 | 전사=플랫폼팀, 프로젝트=리드, 개인=본인 |
| 전사 표준은 사람이 손으로 복사하지 않는다 | 복사하면 즉시 갈라지고 업데이트가 끊깁니다 |
| 강제보다 먼저 표준 제공 | 강제는 되돌리기 어렵고 반발이 큽니다. 유용함을 먼저 증명합니다 |
| 문서 1장으로 답이 나와야 한다 | `docs/02-where-what.md` 가 그 1장입니다 |

## 3. 계층 구조

```
0층  관리자 강제      managed-settings.json           IT 배포. 현재 미사용, 확장 여지로 남김
1층  전역 회사표준    vntg-standard 플러그인           개발플랫폼팀. Git으로 버전 관리
     전역 개인기본    ~/.claude/settings.json         /vntg-setup-global 로 표준 병합 + 개인 취향
2층  프로젝트 팀공유  <repo>/.claude/, .mcp.json, CLAUDE.md   프로젝트 리드. git 커밋
3층  개인            settings.local.json, CLAUDE.local.md    본인. git 제외
```

우선순위: `0층 > CLI 옵션 > 3층 > 2층 > 1층`

### 우선순위가 역순인 것이 왜 문제가 아닌가

개인(3층)이 전사(1층)보다 강한 것은 의도된 설계입니다. 이유:

- `permissions.deny` 는 **모든 층이 합쳐지고 allow보다 항상 우선**합니다.
  따라서 보안 금지선은 1층에 두어도 3층에서 뚫을 수 없습니다.
- 나머지(모델 선택, 허용 명령, 출력 스타일)는 개인/프로젝트가 더 잘 아는 영역이므로
  아래층이 이기는 것이 맞습니다.
- 진짜 강제가 필요한 항목만 0층으로 올립니다.

이 구조라면 "권장으로 시작해서 필요한 것만 강제로 올린다"는 단계적 전환이 가능합니다.

## 4. 왜 플러그인 + Git 마켓플레이스인가

### 대안 비교

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 위키에 설정 스니펫 게시 | 만들기 쉬움 | 각자 복사 → 즉시 갈라짐. 업데이트 전파 불가 | 탈락 |
| 사내 `.plugin` 파일 공유 드라이브 배포 | Git 없이 가능 | 버전 추적 불가, 업데이트 수동, 이력 없음 | 부차 수단 |
| **Git 마켓플레이스** | 버전 관리, MR 리뷰, 이력, `/plugin update` 로 갱신 | Git 접근 권한 필요 | **채택** |
| 관리자 설정 전면 강제 | 확실함 | 프로젝트 자율성 소멸, 초기 반발, IT 배포 인프라 필요 | 나중 단계 |

### Git 마켓플레이스의 결정적 이점

표준 변경이 **코드 리뷰를 거친다**는 점입니다. 보안 정책이나 코딩 규칙 변경이
MR로 올라오고, 리뷰어가 붙고, 이력이 남습니다. 위키 편집으로는 얻을 수 없습니다.

## 5. 플러그인 3분할

```
vntg-standard    전원 필수. 표준 스킬, 표준 MCP, 가드레일, 도구 명령
vntg-backend     백엔드만. Spring/.NET/DB 스킬
vntg-frontend    프론트만. React/TS/접근성 스킬
```

전부 하나에 넣으면 프론트 개발자에게 DB 마이그레이션 스킬이 뜨고, 그 반대도 일어납니다.
스킬은 관련 요청에 자동으로 반응하므로, 관계없는 스킬이 많으면 오작동 확률이 올라갑니다.
필수 1개 + 스택별 선택으로 나눈 이유입니다.

## 6. 핵심 제약: 플러그인이 권한을 배포할 수 없다

이것이 설계에서 가장 중요한 기술 제약입니다.

| 플러그인이 배포 가능 | 배포 불가 |
| --- | --- |
| 스킬, 슬래시 명령, 서브에이전트 | `settings.json` |
| 훅 | `permissions` 규칙 |
| MCP 서버, LSP 서버 | `CLAUDE.md` |
| 출력 스타일, 테마 | `env` |

그래서 권한 정책은 다음 경로로 전달합니다.

```
플러그인이 templates/global-settings.json 을 담아서 배포
        ↓
사용자가 /vntg-setup-global 실행
        ↓
~/.claude/settings.json 에 병합 (덮어쓰기 아님, 중복 제거)
```

**한계**: 사용자가 나중에 지울 수 있습니다. 이는 "권장 수준"이라는 선택의 결과이고,
강제가 필요해지면 0층(관리자 설정)으로 같은 내용을 올리면 됩니다. 내용은 그대로 쓰고
전달 경로만 바뀌므로 전환 비용이 낮습니다.

## 7. 가드레일 설계 (경고 우선)

시크릿 가드 훅은 **차단이 아니라 경고**로 시작합니다.

이유: 오탐이 반드시 발생합니다. 테스트 픽스처의 더미 비밀번호, 문서의 예시 키 등.
초기에 차단으로 걸면 사람들이 훅을 끄는 방법을 찾기 시작하고, 그러면 가드레일 전체가 무력화됩니다.

구현: 훅이 종료 코드 1을 반환합니다. 도구 실행은 계속되고 경고 메시지만 비차단 알림으로
표시됩니다. 종료 코드 0은 stderr가 어디에도 표시되지 않으므로 경고 모드에 쓸 수 없습니다.
차단 모드는 종료 코드 2입니다.

전환 경로: 경고 운영 → 발생 로그로 패턴 정밀화 → 오탐률이 충분히 낮아지면
`VNTG_SECRET_GUARD_BLOCK=1` 을 0층에서 강제.

## 8. 발견성 (전체 이용자가 알기 쉽게)

"쓰기 쉬운 표준"의 핵심은 **필요한 순간에 눈에 보이는 것**입니다. 문서를 읽게 만드는 것에
의존하지 않고 3중으로 배치했습니다.

| 장치 | 언제 보이나 | 무엇을 알려주나 |
| --- | --- | --- |
| 세션 컨텍스트 주입 | 모든 세션 시작 시 | Claude가 표준과 전용 명령의 존재를 알고 먼저 안내 |
| `/vntg-help` | 확인이 필요할 때 | 3층 구조 + "이건 어디에 넣나" 표 |
| `/vntg-doctor` | 문제가 생겼을 때 | 실제 파일 존재 여부 + 어느 층에서 오는지 + 권장 조치 |
| `/vntg-init` | 새 프로젝트 시작 시 | 물어볼 필요 없이 표준 세팅 생성 |
| `docs/02-where-what.md` | 정확히 알고 싶을 때 | 전체 기준표 + 자주 하는 실수 |

`/vntg-doctor` 는 특히 중요합니다. 설정 계층 문제는 "왜 내 설정이 안 먹는지 모르겠다"로
나타나는데, 이때 사람이 5개 파일을 직접 찾아보게 하는 대신 진단 결과를 보여줍니다.

## 9. 도입 단계

| 단계 | 기간 | 내용 | 성공 기준 |
| --- | --- | --- | --- |
| 1. 파일럿 | 2주 | 1개 팀에 적용. 스킬 3개 + 가드레일 | 팀원 전원 설치, 오탐 이슈 정리 |
| 2. 확대 | 4주 | 스택 플러그인 추가. 팀별 온보딩 세션 | 재직자 60% 설치 |
| 3. 정착 | 8주 | 프로젝트 리포에 2층 세팅 확산 | 활성 리포 70%에 `.claude/settings.json` |
| 4. 선택적 강제 | 이후 | `permissions.deny` + 로그인 조직 제한만 0층으로 | 보안팀 요구사항 충족 |

각 단계에서 다음으로 넘어가기 전에 이전 단계 지표를 확인합니다.
설치율이 낮은 상태에서 강제로 넘어가면 "IT가 또 뭘 걸었다"가 됩니다.

## 10. 남은 위험과 대응

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| 사내 Git 접근이 안 되는 구성원 | 설치 불가 | `.plugin` 파일 배포를 보조 경로로 유지 |
| 표준이 낡아서 오히려 방해 | 사람들이 끄기 시작 | 분기 1회 리뷰. 안 쓰이는 스킬은 제거 |
| 스킬이 너무 많아져 오작동 | 관계없는 스킬이 발동 | 스택별 분리 유지. 필수 플러그인은 5개 스킬 이내로 제한 |
| MCP 자격증명 관리 | 시크릿 노출 | `.mcp.json` 은 `${VAR}` 만. 값은 사내 시크릿 매니저 |
| 플러그인이 권한을 못 배포하는 제약 | 표준 우회 가능 | 0층 전환 경로 확보. 우선은 deny 병합으로 실효 확보 |
| `enabledPlugins` 만으로는 미설치자에게 전달 안 됨 | 신규 팀원이 표준 없이 시작 | 온보딩 체크리스트에 `/plugin install` 명시. 장기적으로 조직 콘솔 배포 |
| Claude Code 스펙 변경 | 설정 키가 안 먹음 | 분기 1회 공식 문서 대조. `docs/05-admin.md` 에 확인 절차 명시 |

## 11. 검증 필요 사항

이 설계는 2026-08 시점 Claude Code 문서를 근거로 작성했습니다. 실제 도입 전 아래를 직접 확인하세요.

- [ ] `claude plugin validate` 로 마켓플레이스와 플러그인 매니페스트 검증
- [ ] 사내 Git(자체 호스팅) 리포가 `/plugin marketplace add` 로 정상 클론되는지
- [ ] `.mcp.json` 의 `${VAR}` 환경변수 치환이 동작하는지
- [ ] Windows에서 `python3` 훅이 정상 실행되는지 (Git Bash 없이도)
- [ ] `permissions` 패턴이 의도대로 매칭되는지: `Bash(curl *)`, `Read(//**/.env)`, `Read(/src/**)`
- [ ] 회사 계약이 Team/Enterprise인지 (조직 콘솔 플러그인 배포 가능 여부가 달라집니다)
- [ ] `docs/05-admin.md` 의 관리자 설정 키 목록이 현재 버전에서 유효한지
